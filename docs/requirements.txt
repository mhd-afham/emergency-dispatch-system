2. Dispatchers: Assign resources, monitor incidents, make dispatch decisions

don't directly use the core system)

decisions)

2. Functional Requirements
1. Call Takers
Emergency Call Management
• The system shall allow call takers to receive and log emergency calls from multiple
channels (voice, SMS, mobile app)
• The system shall capture caller information including name, contact number, and
callback details
• The system shall timestamp all incoming calls automatically
Incident Data Entry
• The system shall provide structured forms for incident data entry with mandatory and
optional fields
• The system shall allow call takers to select incident type (Medical, Fire, Rescue) from
predefined categories
• The system shall support free-text description entry for incident details
Location Management
• The system shall provide address geocoding with auto-suggestions
• The system shall allow call takers to manually adjust location pins on an interactive map
• The system shall validate and confirm caller location through SMS/callback loops
Incident Classification
• The system shall allow call takers to assign severity levels (High, Medium, Low) to
incidents
• The system shall support incident code assignment based on emergency type
• The system shall enable priority escalation for critical incidents
Duplicate Detection
• The system shall automatically detect potential duplicate reports based on location and
time proximity
• The system shall alert call takers when similar incidents are found within specified
radius and timeframe
• The system shall allow call takers to merge duplicate incident reports

6. Use Case Descriptions
6.1 Log Emergency Call
Use Case ID: UC-001
Use Case Name: Log Emergency Call
Summary: Call taker receives an emergency call from a citizen, capture incident details,
validate location information, and classifies the incident for appropriate response.
Priority: 5
Pre-conditions: Call taker is logged into the system with appropriate permissions, Emergency
hotline is operational and receiving calls and Geocoding service is functioning
Post-conditions: Emergency incident is logged in the system with unique incident ID, Incident
is classified and ready for dispatcher assignment, Location is validated and geocoded and
Caller information is captured and stored
Primary Actor: Call Taker
Secondary Actor: Citizen
Trigger: Call operator receives an emergency call and needs to log details for appropriate
response
Main Scenario:
1. Call taker receives an emergency call
2. Call taker answers the call and opens incident intake form
3. Call taker captures caller information (name, contact number, callback details)
4. System automatically timestamps the incident.
5. Call taker enters incident details using structured form fields
6. Call taker selects incident type (Medical, Fire, Rescue, etc.) from dropdown
7. Call taker captures location information from caller
8. System provides geocoded address suggestions based on input
9. Call taker validates location using interactive map interface
10. Call taker assigns severity level (High, Medium, Low) based on incident nature.
11. System assigns appropriate incident code automatically
12. Call taker reviews all entered information for completeness.
13. Call taker saves the incident record.
14. System generates unique incident ID and transfers to dispatcher queue.
24
15. System sends incident record confirmation SMS to caller
Branching Actions:
A: Incomplete Location Information (Step 8)
7a. Caller cannot provide precise location
7b. Call taker uses landmark-based geocoding
7c. System provides approximate location options
7d. Call taker adjust pin on interactive map to best suited position
7e. Continue with step 10
B: Duplicate Incident Detected (Step 14)
14a. System detects similar incident within proximity and time window
14b. System displays potential duplicate incidents to call taker
14c. Call taker reviews existing incidents
14d. If duplicate: Call taker merges reports under existing incident ID. If not duplicate:
Call taker confirms new incident creation
14e. Complete step 15
C: Caller Disconnection (Any step)
xa. Call taker saves partial incident information
xb. System marks incident as "Incomplete - Callback Required"
xc. Call taker attempts callback using captured contact information
xd. Resume from last completed step

6.2 Assign Resources
Use Case ID: UC-002
Use Case Name: Assign Resources
Summary: Dispatcher reviews incident details, selects appropriate emergency resources
(ambulances, fire engines), and dispatches them to respond to an emergency situation.
Priority: 5
Pre-conditions: Dispatcher is logged into system with dispatch permissions and Incident has
been logged and classified by call taker
Post-conditions: Appropriate resources are assigned to incident, crew members receive
dispatch notifications, incident status updated to "En Route" and citizen receives notification
with ETA information
Primary Actor: Dispatcher
Secondary Actors: Field Crew and Citizen
Trigger: Admin needs to register a vehicle and make it active for assignments.
Main Scenario:
1. System displays new incident in dispatcher’s console queue with priority indicator
2. Dispatcher selects incident to review details
3. System displays incident information (type, location, severity, special requirements
and notes)
4. System automatically suggests nearest available resources based on:
Incident type (medical → ambulance, fire → fire engine)
Proximity to incident location
Crew certifications and equipment requirements
Current availability status
5. Dispatcher reviews suggested resources on real-time map interface
6. Dispatcher selects preferred resource from available options
7. System calculates estimated response time and travel route
8. Dispatcher confirms resource assignment
9. System sends dispatch notification to the selected crew via mobile app and SMS
10. System starts 30-second acceptance timer
11. Crew leader accepts assignment through mobile app
26
12. System updates incident status to "En Route"
13. System begins real-time GPS tracking of assigned unit
14. System sends ETA notification to citizen via SMS and mobile app push notification
15. System logs assignment details and timestamp
16. Dispatcher monitors unit progress on real-time dashboard
Branching Actions:
A: Manual Resource Override (Step 6)
6a. Dispatcher manually selects different available resource
6b. System validates selected resource meets requirements
6c. System recalculates ETA and route
6d. Continue to step 8
B: Multiple Resource Requirement (Step 4)
4a. If the incident requires both ambulance and fire response, system suggests optimal
combination of resources
4b. Dispatcher reviews and confirms both assignments
4d. System coordinates dual dispatch with separate ETAs and travel routes
4e. Continue with step 9 for each resource
C: No Available Optimal Resources (Step 4)
4a. If all optimal resources are currently assigned or unavailable, system displays next
available resource with delay estimate
4b. Dispatcher chooses to proceed with the next available resource suggested
4c. Continue with step 7
4b1. Dispatcher chooses to wait for resource availability
4b2. System queues incident and keeps checking for resource availability
D: Crew Assignment Timeout (Step 11)
11a. If the crew fails to accept assignment within 30 seconds, system notifies the
dispatcher to either try again or proceed with the auto-reassignment logic
11b. Dispatcher opts to try again
11c. Continue with step 9
11b1. Dispatcher opts to proceed with the auto-reassignment logic
27
11b2. System displays next available resource with delay estimate
11b3. Dispatcher chooses to proceed with the next available resource suggested:
11b4. Continue from step 7
E: Crew Declines Assignment (Step 11)
11a. Crew actively declines assignment (vehicle issue, emergency) and provides reason
11b. System logs decline reason and updates crew status
11c. System immediately initiates auto-reassignment logic and displays next available
resource with delay estimate
11d. Dispatcher chooses to proceed with the next available resource suggested:
11e. Continue from step 7
28
6.3 Plan Shifts
Use Case ID: UC-003
Use Case Name: Plan Shifts
Summary: Shift supervisors creates shifts, assign available crew members, and publish the
schedule.
Priority: 5
Pre-condition: Shift supervisor is logged into the system with scheduling permissions
Post-conditions: Shift schedules created for specified time period, crew assignments are
confirmed and communicated with notifications sent to affected crew members
Primary Actor: Shift Supervisor
Secondary Actors: Field Crew
Trigger: Admin needs assign shifts to crew members
Main Scenario:
1. Shift supervisor logs in and navigates to "Schedule Management"
2. System displays a calendar view showing the current week with any existing
schedules
3. Supervisor selects the time period to create schedules for (next week or next month)
4. System displays the selected time period with standard shift time slots (Day: 8AM4PM, Evening: 4PM-12AM, Night: 12AM-8AM)
5. Supervisor clicks on an empty shift slot in the calendar
6. System opens a shift details form showing the selected date, time, and asking for
staffing requirements
7. Supervisor enters the number of crew members needed and their required roles (EMT,
Firefighter, Driver)
8. Supervisor clicks "Create Shift" and system saves the shift slot with requirements
9. Supervisor clicks on the newly created shift slot to assign crew members
10. System displays the shift requirements and shows a list of available crew members
with their roles and availability status
11. Supervisor selects crew members from the available list using checkboxes
12. System validates the assignments and checks for basic conflicts (overlapping shifts,
excessive hours)
29
13. If validation passes, supervisor clicks "Assign Crew" and system saves the
assignments
14. Supervisor repeats steps 5-13 for other needed shifts throughout the time period
15. When all shifts are created and staffed, supervisor clicks "Publish Schedule" and
system sends notifications to assigned crew members
Branching Actions:
10a. If the available crew members are fewer than required for the shift, system displays
the available crew members with a warning message
10b. Supervisor chooses one of the following options: Leave shift understaffed and add
a note explaining the shortage or contact additional crew members to request overtime
work
11c. Supervisor documents the decision and continues with available assignments
11d. Continue with step 12

6.4 Register Vehicle
Use Case ID: UC-004
Use Case Name: Register Vehicle
Summary: Admin registers a vehicle and submits for shift supervisor approval with notifications
and audit logs.
Priority: 5
Pre-condition: Admin is logged into the system with proper permissions.
Post-condition: The vehicle is active for assignment, linked as needed, notifications are sent,
and audit entries are stored.
Primary Actor: System Administrator
Secondary Actor: Shift Supervisor
Trigger: Admin needs to register a vehicle and make it active for assignments.
Main Scenario:
1. System administrator accesses vehicle registration module.

6.5 Check Vehicle/Equipment Readiness
Use Case ID: UC-005
Use Case Name: Check Vehicle/Equipment Readiness
Summary: Field Crew Leader conducts systematic pre-shift equipment readiness checks using
digital checklists on their mobile app and vehicle’s availability is marked for dispatch based on
inspection results
Priority: 5
Pre-condition: Field Crew Leader is logged into mobile app with appropriate permissions
Post-condition: Equipment readiness status is recorded in the system, Vehicle is marked as
available/unavailable for dispatch based on inspection results and Maintenance work orders
are generated for any failed equipment
Primary Actor: Field Crew Leader
Trigger: Field Crew Leader needs to inspect their assigned vehicle before it can be made
available for emergency dispatch.
Main Scenario:
1. Crew leader navigates to “Vehicle/Equipment Management”
2. System displays assigned vehicle and equipment information
3. Crew member taps "Begin Equipment Check" button
4. System loads the appropriate digital checklist template based on vehicle type
(ambulance or fire engine)
5. Crew member performs vehicle systems inspection (fuel level, oil, battery, coolant,
belts) and enters levels or PASS/FAIL status for each item in the mobile app
6. Crew member conducts exterior inspection (emergency lights, siren, physical
damage) and records PASS/FAIL status in the app
7. Crew member checks running condition and expiry dates of emergency equipment
specific to vehicle type (medical supplies for ambulance, firefighting tools for fire
engine) and enters PASS/FAIL status in the app
8. System validates all information against minimum thresholds and displays results
9. For FAIL items, crew member records detailed description of the problem and selects
urgency level (Critical, High, Medium, Low) from dropdown menu
10. System calculates overall readiness score based on all checklist items and displays
inspection summary
11. If all critical items pass, crew member confirms readiness and ends readiness
check.
