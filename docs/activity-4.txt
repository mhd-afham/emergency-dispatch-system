1. Comprehensive ER Diagram Design

1.1 Entity Identification and Analysis

Based on the functional requirements and user stories from Activities 2 and 3, the following entities have been identified for the Emergency Dispatch System:

Primary Entities:
- User: System users with role-based access (Call Takers, Dispatchers, Field Crews, etc.)
- Incident: Emergency incidents logged through various channels
- Location: Geographic locations associated with incidents and resources
- Vehicle: Emergency vehicles (ambulances, fire engines) available for dispatch
- Crew: Field personnel assigned to vehicles and shifts
- Shift: Work shifts with staffing requirements and schedules
- Equipment: Equipment items associated with vehicles
- EquipmentChecklistTemplate: Standardized checklists for vehicle types
- EquipmentCheck: Individual equipment inspection records
- Assignment: Resource assignments to incidents
- Communication: SMS/push notification history and delivery tracking
- Report: Post-incident reports and analytics
- AuditLog: System audit trail for compliance

2. Database Normalization Process

2.1 Initial Unnormalized Form (0NF)

Before normalization, we identify a representative table that contains all the data in an unnormalized form:

IncidentRecord Table (0NF):
incident_id | caller_name | caller_phone | incident_type | severity | description | address | latitude | longitude | 
assigned_vehicle_plate | vehicle_type | vehicle_make | vehicle_model | crew1_name | crew1_role | crew1_phone | 
crew2_name | crew2_role | crew2_phone | dispatcher_name | dispatcher_phone | equipment1_name | equipment1_status | 
equipment2_name | equipment2_status | equipment3_name | equipment3_status | report_content | report_attachments

Problems in 0NF:
- Repeating groups (crew1, crew2, equipment1, equipment2, equipment3)
- Multiple values in single fields
- Data redundancy
- Update anomalies
- Insertion anomalies
- Deletion anomalies

2.2 First Normal Form (1NF)

Objective: Eliminate repeating groups and ensure atomic values.

Rules Applied:
1. Each cell contains only atomic (indivisible) values
2. Each column contains values of the same type
3. Each row is unique
4. No repeating groups or arrays

Transformation Steps:
1. Separate repeating groups into individual rows
2. Create unique identifiers for each row
3. Ensure all attributes are atomic

Result - Tables in 1NF:

Incident_1NF:
incident_id | caller_name | caller_phone | incident_type | severity | description | 
address | latitude | longitude | dispatcher_name | dispatcher_phone | report_content

VehicleAssignment_1NF:
assignment_id | incident_id | vehicle_plate | vehicle_type | vehicle_make | vehicle_model

CrewAssignment_1NF:
crew_assignment_id | assignment_id | crew_name | crew_role | crew_phone

EquipmentStatus_1NF:
equipment_status_id | assignment_id | equipment_name | equipment_status

Achievements:
✅ Eliminated repeating groups
✅ All values are atomic
✅ Each row is uniquely identifiable
✅ Columns contain homogeneous data types

2.3 Second Normal Form (2NF)

Objective: Eliminate partial dependencies on composite primary keys.

Rules Applied:
1. Must be in 1NF
2. All non-key attributes must be fully functionally dependent on the entire primary key
3. No partial dependencies

Analysis of Functional Dependencies:

In VehicleAssignment_1NF:
- assignment_id → incident_id (full dependency)
- assignment_id → vehicle_plate (full dependency)
- vehicle_plate → vehicle_type, vehicle_make, vehicle_model (partial dependency - problem!)

In CrewAssignment_1NF:
- crew_assignment_id → assignment_id, crew_name (full dependency)
- crew_name → crew_role, crew_phone (transitive dependency - will handle in 3NF)

Transformation Steps:
1. Identify partial dependencies
2. Create separate tables for partially dependent attributes
3. Reference using foreign keys

Result - Tables in 2NF:

Incident_2NF:
incident_id (PK) | caller_name | caller_phone | incident_type | severity | description | 
address | latitude | longitude | dispatcher_id

User_2NF:
user_id (PK) | name | phone | role

Vehicle_2NF:
vehicle_id (PK) | plate_number | vehicle_type | make | model

Assignment_2NF:
assignment_id (PK) | incident_id (FK) | vehicle_id (FK)

CrewAssignment_2NF:
crew_assignment_id (PK) | assignment_id (FK) | crew_id (FK)

Crew_2NF:
crew_id (PK) | crew_name | crew_role | crew_phone

Equipment_2NF:
equipment_id (PK) | equipment_name | vehicle_id (FK)

EquipmentStatus_2NF:
status_id (PK) | equipment_id (FK) | assignment_id (FK) | status

Report_2NF:
report_id (PK) | incident_id (FK) | content

Achievements:
✅ Eliminated partial dependencies
✅ Vehicle attributes properly separated
✅ All non-key attributes fully dependent on primary key
✅ Reduced data redundancy

2.4 Third Normal Form (3NF)

Objective: Eliminate transitive dependencies.

Rules Applied:
1. Must be in 2NF
2. No transitive dependencies (non-key attribute depending on another non-key attribute)
3. All non-key attributes directly dependent on primary key only

Analysis of Transitive Dependencies:

In Incident_2NF:
- incident_id → address → latitude, longitude (transitive dependency)

In Crew_2NF:
- crew_id → crew_role → responsibilities, certification_requirements (potential transitive)

Transformation Steps:
1. Identify transitive dependencies
2. Create separate tables for transitively dependent attributes
3. Use foreign keys to maintain relationships

Result - Tables in 3NF:

User_3NF:
user_id (PK) | email | password_hash | first_name | last_name | phone | role | is_active | last_login | created_at

Incident_3NF:
incident_id (PK) | caller_name | caller_phone | incident_type | severity | description | 
location_id (FK) | status | reported_at | created_by (FK) | assigned_to (FK)

Location_3NF:
location_id (PK) | address | latitude | longitude | location_type | verified | created_at

Vehicle_3NF:
vehicle_id (PK) | plate_number | vehicle_type | make | model | year | status | 
current_latitude | current_longitude | station_location_id (FK) | is_active | registered_at

Crew_3NF:
crew_id (PK) | employee_id | first_name | last_name | role | phone | email | 
certification_level | certification_expiry | hire_date | is_active

Equipment_3NF:
equipment_id (PK) | equipment_name | equipment_type | serial_number | vehicle_id (FK) | 
status | last_check_date

Assignment_3NF:
assignment_id (PK) | incident_id (FK) | vehicle_id (FK) | crew_id (FK) | assigned_by (FK) | 
assigned_at | status | response_time_seconds

EquipmentCheck_3NF:
check_id (PK) | vehicle_id (FK) | crew_id (FK) | template_id (FK) | overall_status | 
check_location_latitude | check_location_longitude | checked_at

EquipmentChecklistTemplate_3NF:
template_id (PK) | vehicle_type | checklist_name | is_active | created_at

Communication_3NF:
communication_id (PK) | incident_id (FK) | recipient_phone | message_type | message_content | 
delivery_status | sent_at | delivered_at

Report_3NF:
report_id (PK) | incident_id (FK) | created_by (FK) | report_type | content | created_at | 
approved_by (FK)

Shift_3NF:
shift_id (PK) | shift_name | start_time | end_time | date | required_crew_count | 
supervisor_id (FK) | status | created_at

CrewShiftAssignment_3NF:
crew_id (FK) | shift_id (FK) | assigned_at | status

AuditLog_3NF:
audit_id (PK) | user_id (FK) | action | entity_type | entity_id | timestamp | ip_address

Achievements:
✅ Eliminated transitive dependencies
✅ Location data properly normalized
✅ All tables in 3NF
✅ Minimized data redundancy
✅ Improved data integrity
✅ Reduced update, insert, and delete anomalies

2.5 Normalization Benefits Achieved

Data Integrity:
- Eliminated update anomalies
- Prevented inconsistent data states
- Ensured referential integrity through foreign keys

Storage Efficiency:
- Reduced data redundancy
- Minimized storage requirements
- Eliminated duplicate information

Maintenance Benefits:
- Single point of truth for each data element
- Easier to maintain data consistency
- Simplified update operations

3. Normalized Relational Schema

3.1 Final Normalized Table Structures

User Table:
CREATE TABLE User (
    user_id VARCHAR(24) PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    phone VARCHAR(20),
    role ENUM('Call Taker', 'Dispatcher', 'Field Crew', 'Supervisor', 'Admin', 'Analyst') NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    last_login TIMESTAMP,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

Location Table:
CREATE TABLE Location (
    location_id VARCHAR(24) PRIMARY KEY,
    address TEXT NOT NULL,
    latitude DECIMAL(10, 8) NOT NULL,
    longitude DECIMAL(11, 8) NOT NULL,
    location_type ENUM('Incident', 'Station', 'Hospital') NOT NULL,
    verified BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Incident Table:
CREATE TABLE Incident (
    incident_id VARCHAR(24) PRIMARY KEY,
    caller_name VARCHAR(255),
    caller_phone VARCHAR(20),
    incident_type ENUM('Medical', 'Fire', 'Rescue') NOT NULL,
    severity ENUM('High', 'Medium', 'Low') NOT NULL,
    description TEXT,
    location_id VARCHAR(24) NOT NULL,
    status ENUM('Reported', 'Assigned', 'En Route', 'On Scene', 'Cleared', 'Closed') DEFAULT 'Reported',
    reported_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    closed_at TIMESTAMP NULL,
    created_by VARCHAR(24) NOT NULL,
    assigned_to VARCHAR(24),
    FOREIGN KEY (location_id) REFERENCES Location(location_id),
    FOREIGN KEY (created_by) REFERENCES User(user_id),
    FOREIGN KEY (assigned_to) REFERENCES User(user_id)
);

Vehicle Table:
CREATE TABLE Vehicle (
    vehicle_id VARCHAR(24) PRIMARY KEY,
    plate_number VARCHAR(20) UNIQUE NOT NULL,
    vehicle_type ENUM('Ambulance', 'Fire Engine', 'Rescue') NOT NULL,
    make VARCHAR(100) NOT NULL,
    model VARCHAR(100) NOT NULL,
    year YEAR NOT NULL,
    status ENUM('Available', 'En Route', 'On Scene', 'Maintenance', 'Out of Service') DEFAULT 'Available',
    current_latitude DECIMAL(10, 8),
    current_longitude DECIMAL(11, 8),
    last_location_update TIMESTAMP,
    station_location_id VARCHAR(24),
    is_active BOOLEAN DEFAULT TRUE,
    registered_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    approved_by VARCHAR(24),
    FOREIGN KEY (station_location_id) REFERENCES Location(location_id),
    FOREIGN KEY (approved_by) REFERENCES User(user_id)
);

Crew Table:
CREATE TABLE Crew (
    crew_id VARCHAR(24) PRIMARY KEY,
    employee_id VARCHAR(50) UNIQUE NOT NULL,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    role ENUM('EMT', 'Paramedic', 'Firefighter', 'Driver') NOT NULL,
    phone VARCHAR(20),
    email VARCHAR(255),
    certification_level VARCHAR(100),
    certification_expiry DATE,
    hire_date DATE NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    created_by VARCHAR(24) NOT NULL,
    FOREIGN KEY (created_by) REFERENCES User(user_id)
);

Assignment Table:
CREATE TABLE Assignment (
    assignment_id VARCHAR(24) PRIMARY KEY,
    incident_id VARCHAR(24) NOT NULL,
    vehicle_id VARCHAR(24) NOT NULL,
    crew_id VARCHAR(24) NOT NULL,
    assigned_by VARCHAR(24) NOT NULL,
    assigned_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    accepted_at TIMESTAMP NULL,
    response_time_seconds INT,
    arrival_time TIMESTAMP NULL,
    cleared_at TIMESTAMP NULL,
    status ENUM('Assigned', 'Accepted', 'Declined', 'En Route', 'Arrived', 'Cleared') DEFAULT 'Assigned',
    FOREIGN KEY (incident_id) REFERENCES Incident(incident_id),
    FOREIGN KEY (vehicle_id) REFERENCES Vehicle(vehicle_id),
    FOREIGN KEY (crew_id) REFERENCES Crew(crew_id),
    FOREIGN KEY (assigned_by) REFERENCES User(user_id)
);

3.2 Constraints and Indexes

Primary Key Constraints:
- All tables have properly defined primary keys
- Ensures entity integrity and uniqueness

Foreign Key Constraints:
- Maintains referential integrity between related tables
- Prevents orphaned records
- Enforces data consistency

Check Constraints:
- Latitude values between -90 and 90
- Longitude values between -180 and 180
- Phone numbers follow valid format
- Email addresses follow valid format

Unique Constraints:
- User.email (prevents duplicate accounts)
- Vehicle.plate_number (ensures unique vehicle identification)
- Crew.employee_id (prevents duplicate employee records)

Indexes for Performance:
- Index on Incident.status for dashboard queries
- Index on Vehicle.status for resource availability
- Index on Assignment.status for active assignments
- Composite index on (latitude, longitude) for location queries
- Index on User.role for role-based access queries
- Index on created_at fields for temporal queries

4. MongoDB-Optimized Design Transformation

4.1 Rationale for MongoDB Schema Design

While the normalized relational schema demonstrates proper database design principles, MongoDB's document-oriented nature allows for strategic denormalization to optimize performance for our real-time emergency dispatch requirements.

Key Considerations for Emergency Dispatch System:
- Sub-second response times for critical operations
- Real-time location tracking and updates
- Frequent read operations for dashboard displays
- Geographic queries for resource positioning
- Offline-capable mobile operations

4.2 MongoDB Schema Design Principles Applied

Embedding Strategy:
- Embed frequently accessed related data
- Reduce join operations for critical queries
- Optimize for read performance in emergency scenarios

Reference Strategy:
- Reference large, independent entities
- Maintain data consistency for shared resources
- Support efficient updates for status changes

// Pre-save validation for incidents
incidentSchema.pre('save', function(next) {
  // Auto-generate incident number if not provided
  if (!this.incidentNumber) {
    const year = new Date().getFullYear();
    const random = Math.floor(Math.random() * 900000) + 100000;
    this.incidentNumber = `INC-${year}-${random}`;
  }
  
  // Validate assignment logic
  if (this.assignment.assignedAt && !this.assignment.vehicleId) {
    return next(new Error('Vehicle ID required when assignment date is set'));
  }
  
  next();
});

// Pre-save validation for vehicles
vehicleSchema.pre('save', function(next) {

    this.status.lastUpdate = new Date();
  }

});

Aggregation Pipelines for Analytics:
const getResponseTimeMetrics = async (startDate, endDate) => {
  return await Incident.aggregate([
    {
      $match: {
        'timeline.reportedAt': { $gte: startDate, $lte: endDate },
        'timeline.arrivedAt': { $exists: true }
      }
    },
    {
      $addFields: {
        responseTime: {
          $divide: [
            { $subtract: ['$timeline.arrivedAt', '$timeline.reportedAt'] },
            1000
          ]
        }
      }
    },
    {
      $group: {
        _id: '$incident.type',
        avgResponseTime: { $avg: '$responseTime' },
        minResponseTime: { $min: '$responseTime' },
        maxResponseTime: { $max: '$responseTime' },
        totalIncidents: { $sum: 1 }
      }
    }
  ]);
};
