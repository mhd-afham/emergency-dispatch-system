1. Comprehensive ER Diagram Design

1.1 Entity Identification and Analysis

Based on the functional requirements and user stories from Activities 2 and 3, the following 12 entities have been identified and implemented in the Emergency Dispatch System:

Primary Entities (Current Backend Implementation):
- User: System users with role-based access (Call Takers, Dispatchers, Field Crews, etc.)
- Incident: Emergency incidents logged through various channels (embeds location data)
- Vehicle: Emergency vehicles (ambulances, fire engines) available for dispatch
- Station: Emergency service stations and facilities
- Crew: Field personnel assigned to vehicles and shifts
- Shift: Work shifts with staffing requirements and schedules
- EquipmentChecklistTemplate: Standardized checklists for vehicle types
- EquipmentCheck: Individual equipment inspection records
- Assignment: Resource assignments to incidents
- Communication: SMS/push notification history and delivery tracking
- Report: Post-incident reports and analytics
- AuditLog: System audit trail for compliance

Design Decision: Location data is embedded within Incident, Vehicle, Station, and Crew entities for optimal performance in emergency scenarios. Equipment data is managed through EquipmentCheck and EquipmentChecklistTemplate models with embedded equipment arrays.

2. Database Normalization Process

2.1 Initial Unnormalized Form (0NF)

Before normalization, we identify a comprehensive table containing all emergency dispatch data in unnormalized form based on our 12 entities:

EmergencyDispatchSystem_0NF:
incident_id | incident_string_id | incident_type | incident_category | severity | description | status | 
caller_name | caller_phone | caller_alternate | caller_method | location_address | location_city | 
location_province | location_lat | location_lng | location_accuracy | landmarks | logged_by_name | 
logged_by_email | logged_by_role | dispatcher_name | dispatcher_email | assigned_vehicle_plates | 
vehicle_types | vehicle_makes | vehicle_models | vehicle_years | vehicle_operational_status | 
crew_names | crew_roles | crew_certifications | crew_specializations | crew_phones | crew_emails | 
station_name | station_address | station_province | station_phone | station_type | 
shift_name | shift_type | shift_start | shift_end | shift_date | shift_supervisor | 
equipment_templates | equipment_categories | equipment_items | equipment_statuses | 
equipment_check_dates | equipment_results | assignment_priorities | assignment_statuses | 
assignment_times | communication_types | communication_content | communication_statuses | 
report_types | report_titles | report_content | audit_actions | audit_timestamps | 
audit_changes | duplicate_incidents | incident_notes

Problems in 0NF:
- Repeating groups (multiple vehicles, crew members, equipment items, communications, reports)
- Multi-valued attributes (crew_specializations, equipment_categories, duplicate_incidents)
- Composite attributes (location data, personal information)
- Data redundancy across all functional areas
- Update, insertion, and deletion anomalies
- Non-atomic values (coordinates, complex nested data)

2.2 First Normal Form (1NF) - Comprehensive Entity Separation

Objective: Eliminate repeating groups and ensure atomic values for all 12 entities.

Transformation Steps:
1. Separate each entity into its own table with atomic attributes
2. Create unique primary keys for all entities
3. Eliminate multi-valued attributes by creating separate records
4. Ensure all attributes contain single, atomic values

Check Constraints:
- Latitude values between -90 and 90
- Longitude values between -180 and 180
- Phone numbers follow valid format
- Email addresses follow valid format

Unique Constraints:
- User.email (prevents duplicate accounts)
- Vehicle.plate_number (ensures unique vehicle identification)
- Crew.employee_id (prevents duplicate employee records)

Indexes for Performance:
- Index on Incident.status for dashboard queries
- Index on Vehicle.status for resource availability
- Index on Assignment.status for active assignments
- Composite index on (latitude, longitude) for location queries
- Index on User.role for role-based access queries
- Index on created_at fields for temporal queries

4. MongoDB-Optimized Design Transformation

4.1 Rationale for MongoDB Schema Design

While the normalized relational schema demonstrates proper database design principles, MongoDB's document-oriented nature allows for strategic denormalization to optimize performance for our real-time emergency dispatch requirements.

Key Considerations for Emergency Dispatch System:
- Sub-second response times for critical operations
- Real-time location tracking and updates
- Frequent read operations for dashboard displays
- Geographic queries for resource positioning
- Offline-capable mobile operations

4.2 MongoDB Schema Design Principles Applied

Embedding Strategy:
- Embed frequently accessed related data
- Reduce join operations for critical queries
- Optimize for read performance in emergency scenarios

Reference Strategy:
- Reference large, independent entities
- Maintain data consistency for shared resources
- Support efficient updates for status changes

const getResponseTimeMetrics = async (startDate, endDate) => {
  return await Incident.aggregate([
    {
      $match: {
        'timeline.reportedAt': { $gte: startDate, $lte: endDate },
        'timeline.arrivedAt': { $exists: true }
      }
    },
    {
      $addFields: {
        responseTime: {
          $divide: [
            { $subtract: ['$timeline.arrivedAt', '$timeline.reportedAt'] },
            1000
          ]
        }
      }
    },
    {
      $group: {
        _id: '$incident.type',
        avgResponseTime: { $avg: '$responseTime' },
        minResponseTime: { $min: '$responseTime' },
        maxResponseTime: { $max: '$responseTime' },
        totalIncidents: { $sum: 1 }
      }
    }
  ]);
};
