1. Comprehensive ER Diagram Design

1.1 Entity Identification and Analysis

Based on the functional requirements and user stories from Activities 2 and 3, the following entities have been identified for the Emergency Dispatch System:

Primary Entities:
- User: System users with role-based access (Call Takers, Dispatchers, Field Crews, etc.)
- Incident: Emergency incidents logged through various channels
- Location: Geographic locations associated with incidents and resources
- Vehicle: Emergency vehicles (ambulances, fire engines) available for dispatch
- Crew: Field personnel assigned to vehicles and shifts
- Shift: Work shifts with staffing requirements and schedules
- Equipment: Equipment items associated with vehicles
- EquipmentChecklistTemplate: Standardized checklists for vehicle types
- EquipmentCheck: Individual equipment inspection records
- Assignment: Resource assignments to incidents
- Communication: SMS/push notification history and delivery tracking
- Report: Post-incident reports and analytics
- AuditLog: System audit trail for compliance

- Vehicle.assignment.currentIncidentId → Incident._id (current assignment)
- Assignment.incident.incidentId → Incident._id (assigned incident)

- EquipmentCheck.vehicleId → Vehicle._id (vehicle being checked)
- EquipmentCheck.crewId → Crew._id (crew performing check)
- AuditLog.activity.userId → User._id (user who performed action)

- Shift.staffing.assignedCrew[].crewId → Crew._id (assigned crew members)

MongoDB Implementation Benefits:
- Embedded relationships eliminate joins for frequently accessed data
- Reference relationships maintain data consistency for normalized entities
- Array references support many-to-many relationships efficiently
- Mixed approach optimizes for both performance and data integrity

2. Database Normalization Process

2.1 Initial Unnormalized Form (0NF)

Before normalization, we identify a representative table that contains all the data in an unnormalized form:

IncidentRecord Table (0NF):
incident_id | caller_name | caller_phone | incident_type | severity | description | address | latitude | longitude | 
assigned_vehicle_plate | vehicle_type | vehicle_make | vehicle_model | crew1_name | crew1_role | crew1_phone | 
crew2_name | crew2_role | crew2_phone | dispatcher_name | dispatcher_phone | equipment1_name | equipment1_status | 
equipment2_name | equipment2_status | equipment3_name | equipment3_status | report_content | report_attachments

Problems in 0NF:
- Repeating groups (crew1, crew2, equipment1, equipment2, equipment3)
- Multiple values in single fields
- Data redundancy
- Update anomalies
- Insertion anomalies
- Deletion anomalies

2.2 First Normal Form (1NF) - Based on Current Implementation

Objective: Eliminate repeating groups and ensure atomic values.

Before normalization, we identify the unnormalized table that would contain all emergency dispatch data:

Emergency_Dispatch_Unnormalized:
incident_id | incident_type | severity | description | status | caller_name | caller_phone | 
caller_address | location_address | location_coordinates | location_province | duplicate_incidents |
status_changes | logged_by_user | logged_by_name | logged_by_role | assigned_vehicle_id | 
vehicle_plate | vehicle_type | vehicle_status | crew_member_names | crew_roles | 
equipment_items | equipment_status

Issues with Unnormalized Form:
- Multiple values in single cells (duplicate_incidents, status_changes, crew_member_names)
- Repeating groups (multiple crew members, equipment items)
- Non-atomic values (location_coordinates as compound value)

Transformation to 1NF:
1. Separate repeating groups into individual rows
2. Create unique identifiers for each entity
3. Ensure all attributes are atomic
4. Maintain current implementation structure

Result - Tables in 1NF (Based on Current Schema):

2.3 Second Normal Form (2NF) - Current Implementation Analysis

Objective: Eliminate partial dependencies on composite primary keys.

Rules Applied:
1. Must be in 1NF
2. All non-key attributes must be fully functionally dependent on the entire primary key
3. No partial dependencies

Analysis of Functional Dependencies in Current Schema:

In Assignment_1NF (composite key: assignment_id):
- assignment_id → incident_id, vehicle_id, crew_id (full dependency - correct)
- assignment_id → assigned_at, assigned_by, dispatch_status (full dependency - correct)
- vehicle_id → plate_number, vehicle_type, make, model (partial dependency - needs separation)
- crew_id → first_name, last_name, role, certification_level (partial dependency - needs separation)

In StatusHistory_1NF:
- status_id → incident_id, previous_status, new_status (full dependency - correct)
- changed_by_user_id → user details (would create partial dependency if included)

Transformation Steps:
1. Separate vehicle attributes from assignment table
2. Separate crew attributes from assignment table  
3. Separate user attributes from incident and status tables
4. Use foreign keys to maintain relationships

Result - Tables in 2NF (Matching Current Implementation):

Incident_2NF:
incident_id (PK) | incidentId | incident_type (medical, fire, rescue, hazmat, traffic, other) | 
incident_category | severity (low, medium, high, critical) | description | 
status (pending, assigned, en_route, on_scene, resolved, cancelled) | 
caller_name | caller_phone | caller_alternate | caller_reporting_method |
location_address | location_city | location_lat | location_lng | location_province | 
location_accuracy | location_landmarks | logged_by_user_id (FK) | assigned_dispatcher_id (FK) |
created_at | updated_at | resolved_at | estimated_response_time | actual_response_time

User_2NF:
user_id (PK) | first_name | last_name | email | phone | employee_id | password_hash |
role (Call Taker, Dispatcher, Field Crew, Supervisor, Admin, Citizen) | 
is_active | last_login | login_attempts | lock_until | email_verified | 
map_zoom | notification_sound | theme (light, dark, system) | created_at | updated_at

AssignedResource_2NF:

Achievements:
✅ Eliminated partial dependencies
✅ User attributes properly separated
✅ All non-key attributes fully dependent on primary key

✅ Structure aligns with current MongoDB implementation approach

2.4 Third Normal Form (3NF) - Current Implementation Aligned

Objective: Eliminate transitive dependencies.

Rules Applied:
1. Must be in 2NF
2. No transitive dependencies (non-key attribute depending on another non-key attribute)
3. All non-key attributes directly dependent on primary key only

Analysis of Transitive Dependencies in Current Schema:

In Incident_2NF:
- incident_id → location_province (direct dependency - correct)
- incident_id → caller_address → location details (potential transitive, but kept embedded for performance)

In User_2NF:
- user_id → role → department (transitive dependency - needs separation)
- user_id → employee_id → department (transitive dependency)

In Vehicle_2NF:
- vehicle_id → station_id → station_name, station_address (transitive dependency)

In Crew_2NF:
- crew_id → role → certification_requirements (transitive dependency)

Transformation Steps (Academic 3NF):
1. Separate role information from user table
2. Separate station information from vehicle table
3. Separate certification requirements from crew table
4. Create lookup tables for enhanced data integrity

3. Normalized Relational Schema (Academic Reference)

3.1 Final Normalized Table Structures (Current Implementation Aligned)

User Table:
CREATE TABLE User (
    user_id VARCHAR(24) PRIMARY KEY,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    phone VARCHAR(15), -- Sri Lankan phone format: +94XXXXXXXXX
    password_hash VARCHAR(255) NOT NULL, -- Bcrypt hash
    role ENUM('Call Taker', 'Dispatcher', 'Field Crew', 'Supervisor', 'Admin', 'Citizen') NOT NULL,
    employee_id VARCHAR(10) UNIQUE, -- Format: EMP123456, sparse (can be null)
    is_active BOOLEAN DEFAULT TRUE,
    last_login TIMESTAMP,
    login_attempts INT DEFAULT 0,
    lock_until TIMESTAMP NULL,
    email_verified BOOLEAN DEFAULT FALSE,
    reset_password_token VARCHAR(255),
    reset_password_expire TIMESTAMP,
    map_zoom INT DEFAULT 12, -- 8-18 range
    notification_sound BOOLEAN DEFAULT TRUE,
    theme ENUM('light', 'dark', 'system') DEFAULT 'system',
    created_by VARCHAR(24),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    last_password_change TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (created_by) REFERENCES User(user_id)
);

Role Table:
CREATE TABLE Role (
    role_id VARCHAR(24) PRIMARY KEY,
    role_name ENUM('Call Taker', 'Dispatcher', 'Field Crew', 'Supervisor', 'Admin', 'Citizen') NOT NULL,
    permissions JSON, -- Role-based permissions
    department VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Station Table:
CREATE TABLE Station (
    station_id VARCHAR(24) PRIMARY KEY,
    station_name VARCHAR(100) NOT NULL,
    address TEXT NOT NULL,
    latitude DECIMAL(10, 8) NOT NULL, -- Sri Lankan coordinate range
    longitude DECIMAL(11, 8) NOT NULL, -- Sri Lankan coordinate range  
    province ENUM('Western', 'Central', 'Southern', 'Northern', 'Eastern', 
                 'North Western', 'North Central', 'Uva', 'Sabaragamuwa') NOT NULL,
    contact_phone VARCHAR(15),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Incident Table:
CREATE TABLE Incident (
    incident_id VARCHAR(24) PRIMARY KEY,
    incident_id_string VARCHAR(50) UNIQUE NOT NULL, -- Format: INC-YYYYMMDD-XXXXX

    description TEXT NOT NULL,
    status ENUM('pending', 'assigned', 'en_route', 'on_scene', 'resolved', 'cancelled') DEFAULT 'pending',
    caller_name VARCHAR(100) NOT NULL,
    caller_contact_number VARCHAR(15) NOT NULL, -- Sri Lankan phone format
    caller_alternate_contact VARCHAR(15), -- Optional alternate contact
    caller_reporting_method ENUM('phone_call', 'mobile_app', 'sms', 'walk_in', 'third_party') DEFAULT 'phone_call',
    location_address VARCHAR(200) NOT NULL,
    location_city VARCHAR(50) NOT NULL,
    location_province ENUM('Western', 'Central', 'Southern', 'Northern', 'Eastern', 
                          'North Western', 'North Central', 'Uva', 'Sabaragamuwa') NOT NULL,
    location_lat DECIMAL(10, 8) NOT NULL, -- Sri Lankan boundaries: 5.9-9.9
    location_lng DECIMAL(11, 8) NOT NULL, -- Sri Lankan boundaries: 79.5-81.9
    location_accuracy ENUM('exact', 'approximate', 'general_area') DEFAULT 'approximate',
    location_landmarks VARCHAR(200),
    logged_by_user_id VARCHAR(24) NOT NULL,
    assigned_dispatcher_id VARCHAR(24),

    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    resolved_at TIMESTAMP NULL,
    estimated_response_time INT, -- Minutes (1-120)
    actual_response_time INT, -- Minutes
    FOREIGN KEY (logged_by_user_id) REFERENCES User(user_id),
    FOREIGN KEY (assigned_dispatcher_id) REFERENCES User(user_id)

3.2 Constraints and Indexes

Primary Key Constraints:
- All tables have properly defined primary keys
- Ensures entity integrity and uniqueness

Foreign Key Constraints:
- Maintains referential integrity between related tables
- Prevents orphaned records
- Enforces data consistency

Check Constraints:
- Latitude values between -90 and 90
- Longitude values between -180 and 180
- Phone numbers follow valid format
- Email addresses follow valid format

Unique Constraints:
- User.email (prevents duplicate accounts)
- Vehicle.plate_number (ensures unique vehicle identification)
- Crew.employee_id (prevents duplicate employee records)

Indexes for Performance:
- Index on Incident.status for dashboard queries
- Index on Vehicle.status for resource availability
- Index on Assignment.status for active assignments
- Composite index on (latitude, longitude) for location queries
- Index on User.role for role-based access queries
- Index on created_at fields for temporal queries

4. MongoDB-Optimized Design Transformation

4.1 Rationale for MongoDB Schema Design

While the normalized relational schema demonstrates proper database design principles, MongoDB's document-oriented nature allows for strategic denormalization to optimize performance for our real-time emergency dispatch requirements.

Key Considerations for Emergency Dispatch System:
- Sub-second response times for critical operations
- Real-time location tracking and updates
- Frequent read operations for dashboard displays
- Geographic queries for resource positioning
- Offline-capable mobile operations

4.2 MongoDB Schema Design Principles Applied

Embedding Strategy:
- Embed frequently accessed related data
- Reduce join operations for critical queries
- Optimize for read performance in emergency scenarios

Reference Strategy:
- Reference large, independent entities
- Maintain data consistency for shared resources
- Support efficient updates for status changes

const mongoose = require('mongoose');

const connectDB = async () => {
  try {
    const conn = await mongoose.connect(process.env.MONGODB_URI || 'mongodb://localhost:27017/emergency_dispatch', {
      useNewUrlParser: true,
      useUnifiedTopology: true,
      maxPoolSize: 10, // Connection pool size
      serverSelectionTimeoutMS: 5000, // Keep trying for 5 seconds
      socketTimeoutMS: 45000, // Close sockets after 45 seconds of inactivity
      bufferMaxEntries: 0, // Disable mongoose buffering
    });
    
    console.log(`MongoDB Connected: ${conn.connection.host}`);
    
    // Set up event listeners
    mongoose.connection.on('error', (err) => {
      console.error('MongoDB connection error:', err);
    });
    
    mongoose.connection.on('disconnected', () => {
      console.log('MongoDB disconnected');
    });
    
  } catch (error) {
    console.error('Database connection error:', error);
    process.exit(1);
  }
};

const getResponseTimeMetrics = async (startDate, endDate) => {
  return await Incident.aggregate([
    {
      $match: {
        'timeline.reportedAt': { $gte: startDate, $lte: endDate },
        'timeline.arrivedAt': { $exists: true }
      }
    },
    {
      $addFields: {
        responseTime: {
          $divide: [
            { $subtract: ['$timeline.arrivedAt', '$timeline.reportedAt'] },
            1000
          ]
        }
      }
    },
    {
      $group: {
        _id: '$incident.type',
        avgResponseTime: { $avg: '$responseTime' },
        minResponseTime: { $min: '$responseTime' },
        maxResponseTime: { $max: '$responseTime' },
        totalIncidents: { $sum: 1 }
      }
    }
  ]);
};
